关于 Harness Engineering，社区里流传最广的一种理解是这样的：模型现在还不够好，所以需要在它外面套一层东西补它的缺陷。等模型变得足够强，这一层东西就会消失，大家又可以回到”直接把任务丢给模型”的简单世界。按这个理解，harness 就是一种临时补丁，是从 AI 辅助编码 到 AI 独立工作 这条路上的过渡形态。这个理解听起来很合理，也很符合人们对技术进步的一般直觉，缺陷被能力抹平，工具被智能取代。但它有一个问题：它解释不了一个很具体的事实。Opus4.6 比 Sonnet3.5 强得多，但从 3.5 时代到 4.6 时代，围绕 Claude Code 的 harness 没有变薄，反而变厚了。query loop 变复杂了，权限策略变细了，compact 机制变成熟了，hook 系统变丰富了。如果 harness 只是能力补丁，模型变强应该让补丁变少才对。实际情况正好相反。这个反直觉的事实逼着人去想一个更根本的问题：harness 到底在做什么？我的回答是：harness 不在补模型的短处，它在承担模型不应该承担的那部分工作。这个分工不是临时的，是结构性的。就像 CPU 再强也需要操作系统，再快的硬盘也需要文件系统，不是因为 CPU 和硬盘不够好，是因为调度和持久化这类事本来就不该由它们来做。模型也一样。有些事情它做不好不是因为它弱，是因为它的工作方式从根本上不适合做这些事。Harness engineering 就是把这些”不该由模型做的事”从模型那里接管过来，交给外部结构去处理。<img 组件都编码了一个假设。这些看似分散的观察其实都指向同一个结构。一、模型的工作方式决定了它不适合做哪些事要理解这个分工从哪里来，得先看清楚 LLM 作为一类系统是怎么工作的。这件事有时候会被掩盖在”让模型更聪明”的讨论下面，但它其实是最根本的出发点。一个 LLM 的基础工作方式可以被压缩成三条事实：自回归生成、无状态推理、对环境的单向读取。自回归生成意味着模型是一个 token 一个 token 往外吐字的。它每一步只能看到已经生成的部分，然后预测下一步。这个过程看起来像在”思考”，其实更像是一段被不断延伸的文本。模型没有一个独立于生成过程的”意图”或”计划”可以事后回头修改。已经生成的 token 就是既成事实，只能在后面补救，不能回去撤销。无状态推理意味着每次 API 调用对模型来说都是一次全新的启动。它没有”上一次对话的记忆”，没有”昨天做过的判断”，没有任何跨调用持久化的东西。开发者看到的”连续对话”，本质上是每一轮都把完整历史重新塞进上下文再调一次。模型以为自己在经历一段连续的交流，实际上它每次只是在看一份被精心编排过的剧本快照。对环境的单向读取意味着模型能看到环境给它的信息，但不能主动感知环境。它知道工具返回了什么，但不知道工具是怎么执行的；它知道文件内容是什么，但不知道这个文件在磁盘上什么位置、被谁读过、是否还会变化。环境对它来说是一组静态输入，不是一个动态过程。这三条事实合在一起，会自动决定几件模型做不好的事。第一件做不好的事是维持连续状态。自回归和无状态放在一起意味着，一段任务如果需要跨多次调用才能完成，模型自己是不知道”前面发生过什么”的。它靠的是被塞进来的对话历史，而对话历史有上限、会稀释、会被后来的内容污染。一个需要连续工作十小时的任务，不可能依赖模型自己的记忆来支撑。第二件做不好的事是判断停止条件。自回归生成的本能是继续吐字。模型在任何一个 token 上都面临”继续还是停”的选择，而它被训练出来的默认偏好是继续，因为训练数据里”把一件事讲完”比”及时停下”出现得频繁得多。让模型自己决定什么时候应该结束一个任务，相当于让一个本能是跑的动物自己决定什么时候该刹车。它也许能做到，但需要付出额外的控制代价，而这个代价往往比在外面装一个刹车要贵。第三件做不好的事是对全局一致性负责。单向读取意味着模型看到的永远是环境的一个切片。它可以非常细致地处理这个切片内的一切，但它不知道这个切片和其他切片之间的关系。让模型”在修 A 的时候考虑到所有可能受影响的 B”，本质上是在要求它同时持有一张它从未见过的全局依赖图。它做不到这件事。不是因为不够聪明，是因为它的信息来源决定了它不可能拥有那张图。第四件做不好的事是对自己的工作进行独立验证。一个刚写完代码的模型，在下一个 token 预测的时候，它对”这段代码好不好”的判断会被”我刚写的”这个事实强烈影响。这不是缺陷，是概率生成器的工作本性：已经被生成的内容会成为后续生成的前提。让同一个模型既实现又验证，等于让同一条概率链在两个阶段都为同一个结论服务。结果往往是它在实现时写出一个看起来像那么回事的东西，然后在验证时给这个东西打一个”看起来像那么回事”的分。 <img 这四件事对应的是四类任务：跨会话的状态持久化、运行循环的停止控制、全局依赖的一致性维护、实现与验证的角色分离。它们都不是”模型做得不够好”这种量的问题，是”模型的工作方式从结构上不适合”这种质的问题。二、分工一旦成立，它就不会因为能力进步而消失上面这个视角把 harness engineering 放进了一个更大的参照系。它不是 AI 工程特有的现象，是每一类系统在扩展能力边界时都会经历的事。CPU 是一个经典的例子。早期计算机没有操作系统，每个程序自己管理内存、自己调度 I/O、自己负责和外设通信。随着 CPU 变强，程序变复杂，这种”每个程序自己管”的模式很快维持不下去。于是操作系统被发明出来，把调度、内存管理、文件系统、中断处理这些事从程序里接管过来，放到一个专门的层里。后来 CPU 变得更强，主频从几 MHz 提到几 GHz，内存从几 KB 提到几十 GB，但操作系统没有消失，反而变得更厚、更复杂、更不可或缺。为什么？因为操作系统本来就不是在补 CPU 的能力短板。它是在承担 CPU 不应该承担的工作。CPU 的工作是执行指令，不是记住昨天发生过什么，不是决定哪个进程先跑，不是维护文件在磁盘上的物理布局。这些事从结构上就不是 CPU 该做的。CPU 再强也不会让它们变成 CPU 的工作。Harness engineering 和 LLM 的关系是完全同构的。LLM 的工作是在给定上下文里生成最可能的下一段 token，不是记住昨天对话里的结论，不是决定一个任务应该什么时候结束，不是维护项目里所有文件之间的依赖图，不是独立地评估自己的输出质量。这些事从结构上就不是 LLM 该做的。LLM 再强也不会让它们变成 LLM 的工作。这个同构关系能直接推出一个重要的推论：随着模型能力提升，harness 的形态会变化，但它不会消失。会消失的是那些针对具体弱点的临时补丁，不会消失的是那些承担结构性分工的基础设施。举个例子。早期 Agent 系统里有一类 prompt 技巧叫”让模型先列出计划再执行”，这是在弥补早期模型规划能力差的缺陷。到 Claude 4 时代，这类技巧几乎不需要了，模型自己会规划。这属于补丁，能力进步把它抹掉了。但 query loop 不会被抹掉，context compact 不会被抹掉，权限边界不会被抹掉，验证机制不会被抹掉。这些不是补丁，是分工。Anthropic 在《Effective harnesses for long-running agents》里有一句话常被引用：每一个 harness 组件都编码了一个关于”模型自身做不到什么”的假设，这些假设会随着模型进步而过时。很多人读到这句话的第一反应是”所以 harness 是临时的”。但这个读法漏掉了一层。这句话的完整含义是：旧的假设会过时，新的假设会取代它们。模型从 Sonnet 4.5 进步到 Opus 4.6 的过程里，”模型会在长对话里过早结束任务”这个假设变得不再成立，对应的 harness 组件（context anxiety 相关的缓解机制）可以简化。但与此同时，一个新假设登场了：越强的模型越倾向于做自信的架构决策，越强的模型越有能力把一件小事滚成一次大重构。新假设带来新组件。分工没有消失，只是重新分配。这个观察有一个听起来反直觉但其实很自然的推论：模型越强，harness 的必要性反而更高，不是更低。一个能力弱的模型造成的破坏是局部的、容易被察觉的：它写的代码通不过编译，它的回答明显离题，它调用工具会报错。这些问题虽然让人头疼，但至少可见。一个能力强的模型造成的破坏是系统的、难以察觉的：它写出看起来没问题的代码，但引入了一个隐蔽的竞态条件；它做出看起来很合理的架构决策，但违反了你项目里一个它不知道的约束；它在一个小任务里顺手重构了一整个模块，每一行改动单看都是改进。弱模型会让你在第一分钟就发现它不行，强模型会让你在一周后才发现它做了什么。这是为什么 Claude 4.6 时代的 harness 比 3.5 时代更厚，不是更薄。能力的进步没有让”刹车”变得不必要，反而让”刹车”变得更重要，因为这辆车跑得比以前快得多。三、三个测试：怎么判断一个系统有没有 harness如果 harness 是结构性分工而不是补丁，那”有没有 harness”这件事就不能靠数组件、数配置文件、数文档行数来判断。一个项目可以有一份写得漂漂亮亮的 CLAUDE.md，但完全没有 harness。另一个项目可能没有 CLAUDE.md，但有扎实的 harness。真正能判断的是这个系统有没有承担前面说的那几类结构性分工。实际中可以用三个问题来测试。第一个问题：这个系统对”失败”的定义是什么？一个没有 harness 的系统里，失败是未定义的。模型跑出错了，系统会崩、会卡住、会无限重试、会把错误原封不动扔给用户，或者更糟，把错误当作正常结果继续用。失败在这种系统里是一种”意外”，意外发生时系统的行为不可预测。一个有 harness 的系统里，失败是被显式命名和分类的。Claude Code 的 query loop 有十种终止原因，每一种都有对应的处理路径。上下文超限不是意外，是一个会触发 compact 的正常事件。工具调用失败不是意外，是一个会触发重试或降级的正常事件。用户中断不是意外，是一个会触发状态保存的正常事件。失败在这种系统里不是”出问题了”，是”系统运行的一个正常阶段”。这个区别听起来微妙，但它直接决定了系统能不能在长时间运行中保持稳定。承认失败是主路径的系统，会把处理失败的代码当作一等公民来写；假装失败是例外的系统，会把处理失败的代码塞进 catch 块里草草了事。第一种系统能扛住十小时的连续任务，第二种系统通常撑不过半小时。Harness Books 第 9 章里有一条原则叫”错误路径就是主路径”，讲的就是这件事。一个成熟的 Agent 系统不是”大部分时间在成功路径上，偶尔掉进错误路径”，是”成功路径和错误路径一直在同时运行，系统随时可能在两者之间切换”。只有这样设计，系统才不会在一次意外到来时整体失控。第二个问题：这个系统的停止条件写在哪里？停止条件是一个特别能反映系统成熟度的东西，因为它是最容易被省略的。很多早期 Agent 系统的停止条件就一条：模型说自己完成了。这相当于让司机自己决定什么时候停车，而且是一个本能是踩油门的司机。一个有 harness 的系统不会把停止权交给模型。它会在运行时定义一套外部终止条件，任何一个被触发都会让循环结束：任务完成信号（这是模型可以参与的，但不是唯一来源）、token 预算耗尽、最大轮次达到、工具调用连续失败、用户打断、hook 阻塞、超时熔断，等等。模型在循环里负责做事，运行时在循环外负责决定什么时候拉闸。这个设计为什么重要？因为它把”停止”这件事从一个需要判断力的问题变成了一个确定性的问题。模型不需要自己想”我是不是该停了”，它只需要继续做事，系统会在合适的时候替它停下。这种分工让模型可以专注于它擅长的事（生成），把它不擅长的事（控制）交给环境。一个没有显式停止条件的系统，在模型能力弱的时候看起来没问题，因为弱模型会自己先歇菜。但一旦模型变强，这种系统就会出问题。强模型不会歇菜，它会一直做下去，直到把一件小任务滚成一次灾难性的重构。这又回到前面那个论点：能力进步不是让 harness 变得不必要，是让它变得更必要。第三个问题：这个系统的状态持久化在哪里？这是最容易被忽视的问题，因为它平时看不出区别。只有当一次对话结束、下一次对话开始的时候，答案才会显现出来。 <img src="https://picx.zhimg.com/50/v2-89a1948fa213ec6e81687045762008ac_720w.jpg?source=2c26e567" data-caption="" data-size="normal" data-rawwidth="813" data-rawheight="687" data-original-token="v2-e1767667bab16f3063431df45d1b7559" class="origin_image zh-lightbox-thumb" width="813" data-original="https://picx.zhimg.com/v2-89a1948fa213ec6e81687045762008ac_r.jpg?source=2c26e567"/> 一个没有 harness 的系统里，状态存在对话历史里。一次 session 结束，状态就消失了。开发者需要在新 session 开始时重新解释项目背景、重新说明之前的决定、重新告诉 Agent 哪些尝试已经失败过。”长期记忆”在这种系统里是一个幻觉，实际存在的只是每一次对话开始时人工注入的背景信息。一个有 harness 的系统里，状态在文件系统上。Anthropic 的 progress.txt 方案、OpenAI 的 plans/ 目录方案，做的都是同一件事：把”上一次对话做到哪里”这件事从模型的内存里搬到磁盘上，让下一次对话可以从那里继续。这个搬运动作看起来很笨，为什么不让模型自己记住？但正是因为它笨，它才可靠。文件系统不会忘记，git 不会忘记，文本文件不会因为对话变长而被稀释。状态持久化这件事本质上是在回答一个问题：这个项目的积累到底属于谁？ 如果积累在开发者的脑子里，那项目换一个人、换一台电脑、换一个时间就从零开始；如果积累在模型的上下文里，那一次对话结束就清零；只有积累在文件系统里，项目才真正拥有自己的记忆。这件事和模型能力没关系，模型再强它也不会把自己的上下文存进 git。存进 git 是 harness 的职责。这三个问题合在一起有一个共同的结构：它们都在问”某件事情的职责被放在了哪里”。失败处理的职责、停止判断的职责、状态持久化的职责。这些职责被放在模型内部，还是被放在模型外部？放在内部意味着依赖模型的自觉和能力，放在外部意味着依赖系统的结构和约束。前者在模型能力弱的时候行不通，在模型能力强的时候也只是看起来行得通。后者从一开始就知道自己在做什么。四、总结：分工意识，而不是补丁意识如果一定要把我的核心观点压成一句话，那就是： Harness engineering 不是在补模型的短处，是在承担模型结构上不该承担的那部分工作。这句话里最关键的词是”结构上”。它意味着这个分工不是某个时代的权宜之计，是 LLM 这类系统在被嵌入真实工程环境时必须完成的一次职责再分配。模型负责它擅长的事：在一段被精心准备的上下文里生成高质量的输出。Harness 负责它不应该做的事：记住历史、判断停止、维护全局一致性、独立验证结果、处理失败、持久化状态。这两部分合起来才构成一个能工作的系统。任何一边单独都不行。顺着这个判断往回看什么是 Harness Engineering：聊聊最近爆火的技术词21 赞同 · 0 评论 文章里列出的八个器官，你会发现它们不是一张”需要做的事”的清单，是一张”职责再分配图”。system prompt 不是在写一段话，是在划定控制面的边界；query loop 不是一个循环，是一个承担停止判断职责的运行时；tool system 不是一堆 API，是一套受管执行接口；context compact 不是一个压缩算法，是一个承担跨轮记忆职责的机制；permission 不是一个开关，是一套承担后果限制职责的策略；recovery 不是一堆 try-catch，是一套承担失败处理职责的主路径；multi-agent 不是在堆角色，是在把验证职责从实现者那里分出来；hook 不是钩子，是把项目级规则写进运行时的接口。理解了这个分工视角之后，很多具体的问题会变得容易判断。下一次你在纠结”这件事应该写进 CLAUDE.md 还是写进 linter”的时候，问自己一个问题：这件事的职责应该在模型内部还是在模型外部？如果是模型可以合理承担的（比如风格偏好、口语化倾向），写进 CLAUDE.md；如果是模型不应该承担的（比如架构不变量、依赖方向、类型安全），写进 linter。写进前者是在给模型加一个希望它记住的便签；写进后者是在把职责彻底交出去。两者看起来效果相似，抗老化能力完全不同。同样的问题可以用来判断一个 Agent 系统值不值得信任。不要数它有多少个 MCP server，不要看它的 prompt 写得多花哨，不要被”完全自动化”这种宣传打动。问那三个问题：失败怎么定义、停止怎么判断、状态怎么持久化。三个问题都能给出清楚答案的系统，是一个承认了分工的系统；三个问题里有任何一个答不上来的系统，是一个还在依赖模型自觉的系统。它也许能演示得很漂亮，但它撑不过真实工程环境里的第一次长跑。从补丁意识切换到分工意识，这是 harness engineering 真正要求从业者做的一次认知转换。它不难理解，但它确实需要被明确说出来，否则人们会在”等模型变强就好了”的想象里一直等下去，而那一天永远不会到来。因为等到的不是 harness 消失的世界，是 harness 变得更复杂、更成熟、更不可见的世界。就像今天没有人会说”等 CPU 变强我们就不需要操作系统了”。那件事不会发生，因为它从一开始就不是那个问题。下一篇讲具体怎么做：在你自己的项目里，如何搭一个承担了上面这些分工的 harness。从 CLAUDE.md 和 AGENTS.md 的写法开始，到 lint 和 CI 的配置，到 spec 和 plan 的沉淀机制。那是 harness engineering 在个人开发者手里真正落地的地方。
